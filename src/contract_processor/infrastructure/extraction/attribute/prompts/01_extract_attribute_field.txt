【最高优先级规则】
1. Attribute 字段定义中的 field_id、meaning、aliases、not_meaning、output 和 extraction_rule 是唯一字段语义依据。`not_meaning` 是硬排除边界：即使词面相近，只要证据只表达被排除概念，就不得输出 found。只处理该字段，禁止创建、改名、拆分或合并目录外字段。
2. 合同理解地图与 Core 上下文仅用于定位和理解交易背景；所有最终结论、原文和规范值必须回到当前合同 PDF 图像核验。它们遗漏、冲突或为空时，不得据此补写或否定合同事实。
3. fields 必须是以当前唯一 field_id 为键的对象；不得增加、遗漏或返回其他字段。顶层只输出 fields，不得输出 document_id 或根级 reason。
4. 非 object 字段严格按 raw_value、reason、status、value 输出。object 字段只输出 properties；对象外层 status 由程序根据直属子字段确定性汇总。每个直属子字段严格按 raw_value、reason、status、value 输出。每个 raw_value 必须直接支撑当前字段或当前子字段，不能因为同处一段、同一标题或词面相近而迁移金额、期限、机构或义务。
5. 每个 reason 必须先基于 raw_value 简述采用、缺失、冲突或排除依据，再以固定输出决定收尾：选择 found 时写“所以接下来的 status=found，value=非 null。”；选择空值状态时写“所以接下来的 status=状态名，value=null。”，并将“状态名”替换为实际选择的 not_found、ambiguous、conflicting、not_applicable，object 直属子字段还可使用 out_of_scope。随后输出的 status 和 value 必须与该决定完全一致；整个 reason（含固定输出决定）不得超过 300 个字符，不得展开完整思维链。
6. 只提交一次符合 JSON Schema 的最终 JSON；不得输出 Markdown、注释、额外解释或第二份 JSON。

【状态与值】
1. found：存在唯一可采用的结果，value 非 null。
2. not_found：已检查可见页面但未发现，value 必须是 JSON null。
3. ambiguous：存在相关候选但无法可靠消歧，value 为 null，并在 reason 中说明。
4. conflicting：存在互不相容候选，value 为 null，并在 reason 中说明。
5. not_applicable：字段对当前合同明确不适用，value 必须为 null。
6. object 直属子字段额外允许 out_of_scope：存在相关原文，但不属于该子字段的业务口径。此时必须保留 raw_value，value 为 null，并说明排除原因。
7. 非 object 字段的非 found 状态均不得携带 value。object 子字段的 ambiguous、conflicting、out_of_scope 必须保留相关 raw_value；not_found/not_applicable 可保留或省略 raw_value。

【原文、证据与规范化】
1. raw_value 只保存合同中可见的最小必要原文；不得填枚举代码、规范值对象、推理过程或 Core 结果。
2. 所有日期、金额、币种、比例、枚举和数组必须符合字段 output 的类型、格式与 extraction_rule。不得由 Core 合同金额、合同日期或主体信息反推 Attribute 值。
3. 数组按合同原文首次出现顺序去重；每个对象数组项必须符合定义的完整结构。句子同时表达事件与期限时，分别提取事件和期限，不能将整句复制到两个不同语义的子字段。不得把银行账号、联系人等与字段无关的信息带入结果。
4. 复杂字段允许只有部分子字段 found；不得为了填满对象而猜测其余子字段。没有可采用结果时按字段或子字段状态返回 null。出现相关但不能按定义唯一采用的编码、机构或条件时，优先输出 ambiguous/null。

# Clause 条款提取目录

> 状态：结构已确定，独立实验工作流已实现，正式工作流尚未实现。  
> 当前规范版本：`0.4`。  
> 目标：与 Core、Attribute 并行提取，形成边界严格、可供后续模型直接阅读和检索的结构化条款层。

## 1. 模块用途

Clause 用于完整提取付款、交付/服务、验收、质保、违约、保密、知识产权、争议解决及其他权利义务条款。它以条款完整性、原文证据和可追溯性为优先目标；不承担 Core 的前置筛选职责，也不与 Attribute 的动态字段发现混用。

因此，`payment_terms`、`delivery_or_service_terms`、`governing_law_or_dispute_resolution` 已从 Core 字段库移出，后续由 Clause 层统一处理，避免摘要式字段提取丢失条款条件、例外和上下文。

Clause 的目标不是再建立一组条款字段，而是把具有自有原文标题或可继承明确父标题的规范性约定转换成按原始顺序排列的条款列表。合同标题、主体、金额、普通产品表和签署资料由 Core 或其他层承接，不能为了追求文本覆盖率污染 Clause。

## 2. 与 Core、Attribute 的边界

- **Core** 保存合同级、跨合同稳定且适合检索过滤的标准字段。
- **Clause** 保存按原始顺序组织的有标题规范性条款，供模型阅读、问答、检索和进一步抽取。
- **Attribute** 发现尚未标准化、但可能具有跨合同统计价值的动态字段。

Clause 可以包含与 Core 相同的原文信息，但不得负责覆盖或纠正 Core 的规范值。Core 和 Attribute 可以引用 Clause 内容，不能用摘要替换 Clause 的完整原文。

## 3. 对外数据结构

[`clause.yaml`](clause.yaml) 是 Clause 输出结构和提取规则的机器可读规范源。合同级输出中的 `clauses` 是一个有序数组：

```yaml
clauses:
  - clause_number: "第三条"
    heading: "付款方式"
    category: "payment"
    source_text: |
      付款方式：合同签订后，甲方应在收到发票之日起十个工作日内支付全部价款。
    page_refs: [2]
```

每个条款项仅包含五个字段：

| 字段 | 是否可空 | 含义 |
| --- | --- | --- |
| `clause_number` | 是 | 原文中的条款编号，或由原文父编号与子标记确定性组合的层级引用。 |
| `heading` | 否 | 子项自有原文标题，或子项没有标题时继承的最近原文父标题。 |
| `category` | 否 | 用于检索和路由的主类别；无法可靠分类时使用 `other`。 |
| `source_text` | 否 | 条款完整原文，表格转换为保持行列关系的 Markdown。 |
| `page_refs` | 否 | 内容实际出现的 PDF 页面序号，跨页时记录全部页面。 |

`clause_number` 不能根据数组位置补造。独立提取子项时，程序可以把父编号与子项标记组合为“四（1）”等字符串，以支持“根据合同第四条第（1）项……”一类准确引用。

程序必须区分顶层编号和子项标记：当锚点开头的“七、”与已有父编号“七”相同时，两者表示同一个编号，不得生成“七七、”；只有“（1）”等真实子层级才与父编号组合。

## 4. 简化决策

- 不输出 `clause_id`。数组顺序足以定位条款；持久化或 RAG 若需要内部唯一标识，由程序根据合同标识和数组下标确定性生成。
- 不输出 `sequence`。数组天然表达排列顺序，原文编号由 `clause_number` 单独承担。
- 不输出 `structured_summary`。后续模型直接读取 `source_text`，避免摘要遗漏条件、例外和上下文。
- 不输出 `reason`、`status` 或 `confidence`。Clause 承担内容保留，不承担逐条业务判定。
- 不要求模型生成法律解释、风险判断或合同中不存在的标题。

这些简化既减少模型生成负担，也避免非原文内容进入合同文本代理层。

## 5. 条款切分与完整性规则

1. 按合同原始顺序输出，以原文编号和版面结构作为主要切分依据。
2. 子项自有标题优先；`（n）标签：正文` 中的标签属于自有标题。子项没有自有标题时，可以继承最近的原文明示父标题并独立提取。自有标题和可继承父标题均不存在时不得提取，也不得根据正文拟造标题。
3. 同一条款跨页时合并为一个条款项，`page_refs` 记录其覆盖的全部页面。
4. 不得只提取已知类别。类别判断失败时使用 `other`，不能因此丢弃内容。
5. 普通产品清单、价格表、主体签署和银行税务资料不属于 Clause。表格只有在具备原文明示标题且自身表达规范性约定时才可提取。
6. `source_text` 必须保留金额、比例、期限、条件、例外、但书、交叉引用及原文排版空白，不得改写为摘要。自有标题校验只清除 `heading` 比较形式中的 Unicode 空白，并以允许字符间空白的正则匹配未经修改的 `source_text`。
7. 质量、质保、保修范围与除外责任、售后服务、维修更换、维护、技术支持、培训和响应时限属于重点内容，不得因没有编号而遗漏有标题条款。

## 6. 分类策略

`category` 是轻量语义标签，不能使非条款内容取得 Clause 资格。优先复用 `clause.yaml` 中的建议类别；质量、质保和售后分别使用 `quality`、`warranty`、`after_sales_service`。

一个条款同时涉及多个主题时只选择最主要的类别，避免增加多标签输出负担。建议类别不是内容白名单；新类型可以使用稳定的 `lower_snake_case` 标签，无法判断时统一使用 `other`。

## 7. 实验工作流与依赖

独立实验入口见 [`experiments/clause_extraction`](../../../experiments/clause_extraction)。当前实验采用分阶段流程：

1. 接收 PDF 渲染器实际提供的合同页面；
2. Step 1 从上到下穷举标题、编号、标签和分点等结构候选，不同时执行条款资格筛选；
3. 程序确定性归一化锚点中明确存在的项目符号和“标签：”结构，并在明确分点或“冒号标题 + 紧邻正文”关系下传播父标题，不根据正文语义拟造标题；
4. Step 1B 用连续索引组全局整理标题、正文、父章节和子条款，所有原子必须恰好进入一个非重叠组或忽略列表；
5. 程序由组首项和下一原子生成开始/硬结束锚点，再将父标题与自身标题融合为只读投影；
6. Step 2 遍历条款组，每次只输出当前组的保留或排除决定，不重写、补充、拆分或合并边界；
7. 程序将保留决定映射回完整条款组，解析自有或继承标题，并组合可引用的层级编号；
8. Step 3 每次携带整份 PDF，只抽取一个已复核单元硬边界内的完整原文；
9. 对数组顺序、标题来源、首尾锚点、页码范围、失败单元、原文重复/包含和编号重复执行程序校验。

Core 与 Clause 的 Step 1 模型任务完全分离，避免 Core 主体、金额和标的数据污染 Clause；两个实验仍使用相同 system message、公共文本和 PDF 图像顺序作为前缀，以利用 vLLM prefix caching。Clause 不依赖 Core 字段是否成功提取，也不依赖 Attribute 字段归并。正式工作流尚未从实验迁移至 `src/`。

## 8. 设计约束

- 条款提取必须只处理程序实际提供的合同页面；合同内页码或总页数仅能依据可见页眉、页脚或页码标识判断。
- 不得以 Core YAML 的 examples、常见模板或外部常识补写条款。
- 不得因为条款无法分类或没有编号而遗漏有标题正文；没有自有标题但存在明确父标题的子项允许继承，二者均不存在时必须排除。
- 不得以任何摘要覆盖或删减 `source_text`。

## 9. 版本记录

### 0.4

- 实验采用“结构穷举 → 全局边界整理 → 逐组资格筛选 → 单条抽取”的分阶段流程。
- 明确 `（n）标签：正文` 的标签属于子项自有标题，自有标题优先于父标题。
- 允许无自有标题的子项继承最近的原文明示父标题；相应原文不强制重复父标题。
- 允许程序由原文父编号和子项标记确定性组合层级引用，不使用浮点数或数组位置造号。
- Step 1B 只输出结构原子索引组，硬校验完整核销、连续、有序和非重叠，避免标题/正文重复与父子包含。
- Step 2 改为遍历“融合标题 + 来源原子 + 首尾硬边界”的只读投影，每次只生成 `reason + include/exclude`。
- Step 3 必须包含开始锚点且不得包含结束锚点；最终结果增加原文重复、包含及编号重复硬校验。
- 编号组合支持 `2.1` 和 `7.1`，避免再次生成 `七七、`、`71.` 等错误引用。
- 对锚点中的显式项目符号和标签执行可审计的程序归一化，并一次收集全部业务校验错误。

## 1. 模块用途

每份合同生成一份固定格式的合同级摘要，后续只对该摘要生成一个向量，用于快速召回语义相近的合同。

机器可读的栏目、重试和渲染策略位于
[`data/definitions/contract_summary.yaml`](../../data/definitions/contract_summary.yaml)；本文件
只保存设计说明和人工审核规则。

摘要生成是独立关键节点：多模态模型直接阅读完整原 PDF，不以 Core、Attribute 或 Clause 的提取结果作为生成输入。这样可以避免字段遗漏、条款切分和优先级筛选成为摘要的信息瓶颈。

Core、Attribute 和 Clause 仍有独立价值：它们作为合同向量记录的元数据用于精确过滤、召回后展示和进一步处理，也可用于离线评估摘要，但不覆盖摘要从原文得到的事实。

> **事实来源：** 摘要模型直接读取完整原始 PDF；Core、Attribute 与 Clause 只作为元数据或离线评估依据，不能成为摘要生成输入。

## 1.1 Abstract 内部处理管线

```text
共享 PDF 页面 + 摘要栏目策略
  → 初次调用：一次生成全部六个固定栏目
  → JSON Schema / 栏目业务校验
  ├─ 全部通过 → 保留候选
  └─ 存在失败栏目
      → 逐失败栏目生成纠错指引（串行）
      → 单栏目受约束重试（最多策略规定次数）
      → 单栏目校验
      ├─ 通过 → 仅替换当前栏目
      └─ 仍失败 → 继续该栏目重试 / 最终失败
  → 最终全栏目校验
  → 固定顺序渲染摘要文本
  → Abstract StageResult
```

初次调用和每次重试都直接读取完整原始 PDF；Core、Attribute 与 Clause 结果均不作为摘要
输入。局部重试只携带当前栏目的策略与可执行校验反馈，不回传上一次完整候选，因此不会让
无效事实成为新的提示词锚点，也不会重写已通过的其他栏目。

若某一栏目在策略规定的次数内仍不能通过 JSON Schema 或业务校验，整个 Abstract 阶段失败，
不会生成部分成功的摘要或进入向量流程。模型响应、校验信息与重试指标只在内存中传递；实验
入口如需保存诊断材料，必须在 `experiments/` 内完成。

> **全有或全无：** 任一栏目在策略规定次数内仍不合格时，整个 Abstract 阶段失败；不得生成部分成功摘要或进入向量流程。

## 2. 固定摘要格式

所有合同使用相同栏目及顺序：

```text
【合同编号】
{合同自身明确标注的编号}

【合同标题】
{原文正式标题}

【相关方】
{合同权利义务主体及明确角色}

【时间】
{签订日期、明确生效信息、合同整体有效期}

【主要内容】
{交易主体、类型、主要标的、明确总金额和必要产品/服务说明}

【关键履约约定】
{付款、交付/服务、验收、质量/质保、违约/解除、争议解决}
```

缺失栏目仍保留标题，正文留空，不写“未知”“未发现”等无检索价值的占位内容。程序在内存
metrics 中记录最终摘要字符数，但不设置字符数硬上限，避免复杂合同因信息完整而被判失败；
正式服务不为该指标写报告。

> **固定格式：** 六个栏目及其顺序不可变；缺失事实保留栏目标题但正文留空，不能用“未知”或模型推断补位。

## 3. 生成接口与工作流

正式实现位于 `src/contract_processor/infrastructure/extraction/abstract/`，独立实验入口为
[`experiments/contract_summary_generation/run.py`](../../experiments/contract_summary_generation/run.py)：

```bash
python experiments/contract_summary_generation/run.py --pdf "data/input/example.pdf"
```

处理顺序：

1. 程序把完整 PDF 全量渲染为按物理页码排列的图像；超过页数安全上限时失败，不截断合同。
2. 模型在一次请求中提取全部六个栏目，以共享完整合同上下文。
3. 严格 JSON Schema 和程序业务规则逐栏校验。
4. 将失败栏目的程序错误转换成可执行的中文纠错说明，再逐栏局部重试；每次仍提供完整 PDF，但只要求重新输出该栏目。
5. 程序合并通过的局部结果、执行最终校验并按固定顺序渲染文本。

公共文本和全部页面图像置于消息前部，栏目任务置于末尾。初次请求和局部重试共享稳定的多模态前缀，以便 vLLM prefix caching 复用计算。

> **重试边界：** 局部重试只接收当前栏目的策略和可执行纠错说明，不接收上一次完整候选；模型仍须重新阅读原始 PDF。

## 4. 栏目协议

每个栏目统一使用以下证据和状态结构：

| 字段 | 含义 |
| --- | --- |
| `evidence_text` | PDF 中可直接核对的最小必要原文；允许为空。 |
| `page_refs` | 证据所在的物理 PDF 页码，升序且不重复。 |
| `reason` | 解释证据为何支持当前状态及摘要，不能为空。 |
| `status` | `found`、`not_found`、`ambiguous`、`conflicting` 或 `not_applicable`。 |

摘要内容根据栏目语义使用以下字段：

| 栏目 | 摘要字段 | 规则 |
| --- | --- | --- |
| 合同编号、合同标题、主要内容 | `summary_text` | 单个字符串。 |
| 相关方 | `summary_items` | `{role, name}` 对象数组；角色和一个主体完整名称分开输出。 |
| 时间 | `summary_items` | `{type, text}` 对象数组；`type` 为时间语义，`text` 为不带展示标签的事实文本。 |
| 关键履约约定 | `summary_items` | `{type, text}` 对象数组；`type` 为履约类别，`text` 为不带展示标签的事实文本。 |

时间项的 `type` 只允许 `signing_date`、`effective_date`、`effective_info` 和 `validity_period`。履约项的 `type` 只允许 `payment`、`delivery_service`、`acceptance`、`quality_warranty`、`breach_termination` 和 `dispute_resolution`。程序将类型与角色确定性渲染为中文标签，并统一添加全角冒号，从而消除半角/全角冒号或标签遗漏造成的格式失败。

非 `found` 状态下，对应的摘要字段必须为 `null`。程序逐项校验数组元素，再用换行符确定性连接；不依赖模型控制 JSON 字符串中的标签和换行。

模型必须能够如实返回空值。`contract_number` 未找到、歧义或冲突时保留空栏目并继续生成摘要，不能促使模型根据文件名或模板捏造编号。文档身份由程序计算，与栏目状态无关。

主要栏目边界如下：

- 合同编号只接受当前合同自身明确标注的合同号或协议号，排除项目编号、订单号、原合同编号、税号和账号。
- 合同标题只接受 PDF 正文明确呈现的正式标题，不从文件名或交易内容概括。
- 相关方只保留合同权利义务主体；排除代表人、联系人、开户行、账号、税号等信息。业务角色不明确时使用甲方、乙方等原文称谓。
- 时间只保留签订日期、明确生效日期、生效机制和合同整体有效期；付款、交付、验收、质保等期限属于关键履约约定。签订日期本身不是生效依据，模型不得据此推断“签订即生效”。
- 主要内容自然表达交易和主要标的；总金额必须由原文明确，不从单价或阶段款计算。
- 关键履约约定按固定语义顺序压缩高价值事实，合并重复约定，不保留普通套话。

> **栏目边界：** 非 `found` 状态必须输出空摘要值；合同编号、标题、相关方、时间和履约约定均不得从文件名、模板或其他栏目推断。

## 5. 校验与失败语义

程序除校验结构外，还检查证据和页码配对、页码范围、合同编号原文包含关系以及敏感信息误入。相关方的角色与名称由独立字段承载；时间和关键履约类别由 JSON Schema 枚举约束；所有中文展示标签及冒号均由程序生成。上述规则用于阻止主体资料或履约期限进入错误栏目，并保证时间和履约类别顺序稳定。

最终摘要字符数保留在内存 validation 和 metrics 中，只作为质量观察信息，不参与通过/失败判定。若后续需要控制摘要冗余，应根据真实样本长度分布设计压缩策略，而不是采用未经验证的统一硬阈值。

局部重试次数由策略中的 `max_retries_per_section` 控制。达到上限仍不合格时正式服务抛出
错误，不返回成功候选，也不会把未通过的内容送入向量流程。需要保留诊断材料时由实验包装
层负责，正式服务不写文件。

每条业务校验问题包含三个职责分离的字段：

| 字段 | 用途 |
| --- | --- |
| `code` | 稳定错误码，用于程序分支、测试和统计。 |
| `internal_message` | 保留栏目路径和具体值的内部诊断信息，用于开发及人工审计。 |
| `retry_guidance` | 告诉模型“哪里不符合要求、如何修正、哪些事实边界不能改变”的自然语言说明。 |

局部重试 Prompt 只注入 `retry_guidance`，不传上一次完整候选，避免错误事实锚定模型。纠错说明不作为事实来源；模型必须重新阅读 PDF，并以页面证据为准。若重试响应本身不符合 JSON Schema，下一次可用重试机会会收到专门的结构完整性说明。

程序不执行摘要与 `evidence_text` 之间的字符级数字包含关系校验。两者由同一次模型生成，字符比较既不能独立证明 PDF 事实，又容易被空格、全半角、单位和日期格式差异误导。Prompt 仍要求摘要不得增加证据外事实；数字、金额、比例和日期由 `evidence_text`、`page_refs` 与人工审计核验。

> **校验边界：** 程序负责结构、页码、敏感信息与栏目语义门禁；数字和事实最终仍以原 PDF 证据与专家审计确认，不能依赖字符串包含关系裁决。

## 6. 向量记录

每份合同最终只创建一条合同向量记录：

```json
{
  "id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "text": "【合同编号】\nHT-2026-0018\n\n【合同标题】\n...",
  "vector": "由 text 生成的向量",
  "metadata": {
    "document_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "contract_number": "HT-2026-0018",
    "core": {},
    "attribute": [],
    "clause": []
  }
}
```

- `document_id` 和向量主键直接使用原始 PDF 文件完整字节流的 SHA-256 小写值。
- SHA-256 是所有文档的主身份，不是合同编号缺失时的回退；模型不参与生成。
- `contract_number` 允许为 null，也允许不同文件具有相同编号；它只作为展示和精确过滤元数据。
- 完全相同的文件字节得到相同 ID，任意字节变化得到新的文档 ID。
- 只有 `text` 进入 Embedding 模型；`metadata` 不参与摘要向量计算。

> **向量职责：** 合同摘要向量只编码固定摘要正文；`document_id` 是文件身份，`contract_number` 只是可空展示与精确过滤元数据。

## 7. 依赖与注意事项

- 多模态服务、采样参数、上下文长度和视觉页数上限来自 `configs/settings.yaml`。
- 文档身份遵循 [合同文档身份协议](../architecture/document-identity.md)。
- vLLM 的 `--limit-mm-per-prompt` 图像数量必须覆盖一次请求的合同页数。
- 与 Core、Clause 组成正式工作流时，system、公共 PDF 规则、页面图像和页面上下文必须遵循 [MLLM Prompt 共享前缀设计](../architecture/mllm-prompt-prefix.md)；摘要任务规则只能放在公共图像前缀之后。
- 摘要不能覆盖 Core、Attribute 或 Clause 的结构化结果与原文证据。正式工作流不执行跨产物自动一致性校验；专家在最终校验时对照原始 PDF 直接确认和修正，随后一次性落盘。整体流程见[合同信息化处理工作流](../architecture/contract-information-workflow.md)。
- 摘要结构、Prompt 或 Embedding 模型变化后，需要重新生成合同摘要及向量。
- 实验包装器运行方式和 `result.json` 说明见[实验 README](../../experiments/contract_summary_generation/readme.md)。

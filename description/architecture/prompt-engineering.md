# 提示词工程规范

> **适用范围：** 本规范适用于项目中所有由模型阅读或生成的提示词，包括公共 PDF 前缀、任务提示词、字段定义注入、实验提示词和重试反馈。
>
> **规范目的：** 在不牺牲业务约束、可审计性和机器校验的前提下，使模型输入具有清晰的阅读顺序与稳定的决策边界。

---

## 1. 与其他规范的关系

本文件定义提示词的通用表达和编排规则；它不替代各任务的业务规则、JSON Schema 或本地校验。

| 文档 | 职责 |
| --- | --- |
| 本文 | 提示词的内容顺序、判断摘要和结构化信息呈现方式。 |
| [MLLM Prompt 共享前缀设计](mllm-prompt-prefix.md) | 多模态输入的 P0～P3 分层、共享前缀和缓存边界。 |
| 字段目录及任务文档 | Core、Attribute、Clause、摘要和字段发现的业务口径、输出契约与失败处理。 |
| 动态 JSON Schema 与本地校验 | 约束模型响应的机器契约；不得由提示词的自然语言替代。 |

> **优先级：** 任务专属规则可以比本文更严格，但不得违反本文的通用规则。若任务的机器契约与提示词表述不一致，以机器契约为准，并应立即修正提示词。

---

## 2. 总体编排原则

提示词应按模型完成任务的自然顺序组织：先理解任务和事实边界，再给出判断依据，最后输出可消费的决定。不要在模型尚未阅读规则或证据前放置最终结论、预期值或决定性锚点。

```text
任务目标与边界
  → 事实来源与可用上下文
  → 字段定义、判断规则与排除条件
  → 输出要求与校验约束
  → 简短判断摘要
  → 最终结构化决定
```

### 2.1 决策内容后置

- 任务的最终值、状态、关系分类、是否纳入等**实际消费的决定**应置于相关依据之后。
- `reason` 必须先解释采用、缺失、冲突或排除的最小必要依据，再以固定格式收束到后续决定。
- 不应在提示词开头提供可能锚定模型的答案、默认结论或示例决定；确有 few-shot 示例时，示例必须清楚标明为示例，且位于规则之后。
- 公共前缀与任务后缀的物理位置仍须遵守 [MLLM Prompt 共享前缀设计](mllm-prompt-prefix.md) 的 P0～P3 约束；本节仅规定每个任务内容内部的语义顺序。

### 2.2 可审计摘要，不要求完整思维链

`reason` 用于记录可供人工复核的简短判断摘要，不是完整 CoT，也不得要求模型展开逐步、隐含的思维过程。

摘要应只包含：关键原文事实、适用或排除的规则，以及它如何支持本次决定。它不应复述全部字段定义、长篇摘抄合同，也不应复制复杂对象或数组的完整规范值。

## 3. `reason` 与最终决定

### 3.1 固定顺序

当输出包络同时含有原文、判断摘要、状态和值时，键与生成顺序固定如下：

```yaml
raw_value: 原始合同表述或 null
reason: 简短判断摘要；所以接下来的 status=..., value=...
status: 最终状态
value: 规范化后的最终值或 null
```

`reason` 必须紧邻并先于它所解释的 `status` 与 `value`。对象字段由直属子字段各自遵守这一顺序；不在顶层或对象外层重复生成脱离具体决定的 `reason`。

### 3.2 固定收束格式

`reason` 的末尾必须明确声明接下来的决定，固定采用以下格式：

| 决定类型 | `reason` 末尾格式 |
| --- | --- |
| 已找到可采用值 | `所以接下来的 status=found，value=非 null` |
| 未找到、歧义、冲突、不适用或超出范围 | `所以接下来的 status=<实际状态>，value=null` |
| 字段发现的归属比较 | `因此 relation=<relation 字段值>` |

> **一致性要求：** 固定收束只是在自然语言摘要中对后续结构化结果作出承诺；最终 `status`、`value` 或 `relation` 必须与其完全一致。二者不一致时，应由 Schema、业务校验或重试逻辑拒绝该响应。

当前 Core、Attribute 与字段发现的状态集合、长度限制和任务特例分别以其领域文档为准。除非任务文档另有更严格限制，`reason` 应保持一至两句，只表达最小必要依据。

## 4. 结构化信息的提示词呈现

### 4.1 默认使用 YAML 或项目符号

向模型展示字段定义、判断条件、输入上下文和任务步骤时，默认使用 YAML 风格层级或项目符号。它们应表达业务语义，而不是直接粘贴机器响应 JSON。

```yaml
field:
  field_id: contract_number
  name: 合同编号
  meaning: 用于业务定位的合同编号
  output:
    type: string
    nullable: true
  extraction_rule: 仅采用合同明确标注的编号；缺失或无法消歧时不推断。
```

```text
- 事实来源：完整原始 PDF。
- 可用辅助上下文：页面主题与成功字段的简洁规范值；它们不是事实来源。
- 判断要求：仅采用合同明确表述；不能消歧时保留相关原文并输出空值状态。
```

### 4.2 JSON 的适用边界

```text
不推荐：在提示词正文中直接粘贴大段 JSON 字段定义或结果示例。
推荐：用 YAML / bullet 解释业务需求；将 JSON Schema 通过模型接口或程序约束响应结构。
```

JSON 仍适用于以下场景：

- 模型接口的结构化输出契约；
- 程序传输、持久化、解析和测试断言；
- 必须展示精确 JSON 语法的极短反例或输出示例。

即使使用 JSON Schema，也应在提示词中用 YAML 或项目符号补充模型需要理解的业务含义、边界和判断顺序；不得假定 Schema 本身足以表达业务规则。

## 5. 提示词编写与审查清单

新增或修改提示词时，应逐项确认：

- [ ] 任务目标、事实来源、业务规则、输出要求与最终决定的顺序清晰；实际消费的决定位于依据之后。
- [ ] `reason` 是可审计的短摘要，而非完整 CoT；其末尾采用适用的固定收束格式。
- [ ] 结构化业务需求以 YAML 或项目符号呈现，没有无必要的大段 JSON。
- [ ] JSON Schema 仍由程序或接口提供，并与提示词中的状态和值规则一致。
- [ ] 示例不会在任务开始处锚定模型；示例与规则、字段定义和输出契约不存在冲突。
- [ ] 修改公共多模态前缀或任务后缀时，已同时检查前缀缓存、版本计算和对应任务的领域文档。

---

## 6. 实现与维护边界

- 公共 PDF 前缀由 `src/contract_processor/application/prompts/pdf_prefix.py` 统一组装；其输入分层与缓存约束见 [MLLM Prompt 共享前缀设计](mllm-prompt-prefix.md)。
- 字段定义应由专用渲染函数压缩为可阅读的 YAML 风格文本；例如 `core_fields.py` 负责递归呈现字段 `output` 的业务语义。
- 任务 Prompt 文件应保留任务专属规则，不在路由、CLI 或模型客户端中零散拼装业务提示词。
- 改动正式 Prompt 文件后，应确认 `prompt_version` 的计算范围覆盖新增或修改的文件，并运行相应的提示词与抽取回归测试。

> 本规范描述的是提示词表达与审查标准。具体字段定义、状态枚举、输出 Schema、重试次数和业务门禁，必须以对应模块的机器规范及领域文档为准。

## 1. 模块用途

入库是专家终审之后单独调用的业务能力，与自动提取流程逻辑相连，但不接入合同提取
LangGraph，也不依赖 Core、Attribute、Clause 或 Abstract 的提取服务。入库自身使用一张
独立四节点 LangGraph 完成准备、两路并行向量化和持久化。前端接收保留空值和提取
证据的完整 JSON 包络，专家只修改字段值，不执行字段结构删除；确认后回传完整结果以及
审核员、审核时间和审核意见。

入库模块负责：

- 校验终审包络与原始 PDF 的 `document_id`；
- 根据终审 `value` 生成不含无效空字段的 Elasticsearch 稀疏投影；
- 按 `document_id` 保存 PDF 源文件；
- 生成检索向量和合同视觉向量；
- 在正式写入前执行文件级和业务合同级重复判断；
- 经专家确认后安全替换已有重复版本。

> **调用边界：** 入库只接收专家终审后的完整对象；自动提取工作流不直接写入正式存储，也不直接调用入库用例。

## 2. 总体流程

```text
专家确认对象 + 原始 PDF
  → 计算原始 PDF SHA-256
  → SHA-256 精确判重
    ├─ 已存在：按幂等提交处理
    └─ 不存在
        → VL-Embedding 生成合同视觉向量
        → Elasticsearch KNN 召回 Top-K 相似合同
        → VL 模型逐一比较新合同与候选合同
        → 输出重复关系及证据
        → 专家确认是否替换
        → 保存新 PDF、稀疏元数据和全部目标向量
        → 激活新版本
        → 清理被替换的旧版本
```

哈希、向量召回和 VL 判断分别承担不同职责：

1. SHA-256 只判断原始字节完全相同，结果是确定性的；
2. VL-Embedding 只负责从已有合同中召回可能重复的候选，不能直接决定删除或合并；
3. VL 模型结合两份合同的页面、主体、编号、金额、页数和内容差异进行精判；
4. 涉及旧版本删除的最终决定必须由专家确认。

向量召回应使用 Top-K 候选，而不是只比较第一名。具体 K 值、相似度阈值和自动跳过阈值
需要通过真实合同集实验确定，不在本设计阶段硬编码。

> **判重职责分离：** SHA-256 判断文件字节是否相同；向量只召回候选；VL 模型只提供比较结论；涉及替换或删除的业务决定必须由专家确认。

## 3. 身份与重复关系

`document_id` 继续使用原始 PDF 字节的 SHA-256，表示一个确定的文件版本。压缩、重新导出、
重新扫描或增删页都会产生新的 `document_id`，这是正确的文件身份语义。

重复判断解决的是更高层的业务身份问题。后续实现可引入 `contract_id`，将多个
`document_id` 关联到同一业务合同：

```text
contract_id
├── document_id A：电子原件
├── document_id B：压缩版本
└── document_id C：重新签章版本
```

VL 精判的机器结果至少区分：

| 判定 | 语义 | 默认业务动作 |
| --- | --- | --- |
| `exact_duplicate` | 可见合同内容相同，仅文件编码、压缩或载体不同 | 提示专家确认是否用新文件替换 |
| `same_contract_different_version` | 同一业务合同，但存在增删页、条款、签章等差异 | 不自动删除；展示差异后由专家决定 |
| `related_document` | 补充协议、附件、订单等相关但独立的文件 | 独立保存并建立关联 |
| `different_contract` | 不是同一业务合同 | 创建新的业务记录 |

模型输出必须包含命中候选的 `document_id`、置信度、差异证据和简短理由。模型结论不作为
唯一约束，也不能直接触发文件删除。

> **身份边界：** `document_id` 表示文件版本，未来的 `contract_id` 才表示业务合同身份。二者不能互相替代。

## 4. PDF 保存协议

专家确认后，PDF 源文件按以下形式保存：

```text
<configured_document_root>/<document_id>.pdf
```

存储根目录必须由配置提供，不写入领域模型，也不能向前端暴露服务器绝对路径。
Elasticsearch 使用同一个 `document_id` 作为文档 `_id`；查询命中后，后端依据
`document_id` 从文档存储读取原始 PDF。ES 中保留原始文件名、文件大小和 MIME 类型用于
展示，但不依赖原始文件名定位文件。

文件规模较大时可以按哈希前缀分层，例如
`<root>/ab/cd/<document_id>.pdf`，但这不改变对外身份协议。

## 5. 终审对象与空字段裁剪

### 5.1 终审对象是完整审计记录

前端不删除字段。审核员认为某个字段不应入库时，只需将该字段最终 `value` 置为 `null`。
入库边界以终审 `value` 为准：

- 标量字段的最终 `value` 为空时，整个字段不进入 Elasticsearch 检索投影；
- 复合字段递归删除空子字段，全部子字段为空时删除父字段；
- 空数组按空值处理；
- 即使空值字段仍携带 `raw_value`、`reason` 或旧的 `status: found`，也不进入正式检索元数据。

回传的追溯信息首期只要求审核员、审核时间和审核意见。`ingested_at`、请求 ID 等运行信息
由后端生成，不增加前端审核负担。

### 5.2 Elasticsearch 使用稀疏投影

正式待入库包络固定为：

```text
document_id
review
├── reviewer
├── reviewed_at
└── comment
result
└── 与 production 单文件结果完全相同
```

`ContractReviewConfirmation` 已实现该包络的严格 DTO：禁止额外字段，审核时间必须带时区，
并在模型构造时校验外层与 `result` 内的 `document_id` 一致。

> **完整对象 / 稀疏投影：** 终审对象保留状态、原文与理由；索引只接收具有可采用非空 `value` 的事实。审核信息不能因检索裁剪而丢失。

## 6. 向量存储职责

一份正式合同允许保存多个用途不同的向量字段：

| 向量字段 | 输入 | 用途 |
| --- | --- | --- |
| `abstract_vector` | 固定格式 Abstract 正文 | 面向用户问题的合同级语义检索 |
| `document_visual_vector` | 合同 PDF 页面的图像或图文混合输入 | 上传合同的近重复候选召回 |
| `contract_name_vector` | 专家确认的合同名称 | 合同名称语义检索 |
| `product_names_vector` | 专家确认并规范化后的产品名称集合 | 产品语义检索 |

`document_visual_vector` 是入库时必须额外保存的合同级视觉向量。它不能复用
`abstract_vector`：前者服务于跨版式、扫描件和压缩版本的近重复召回，后者服务于合同内容
检索。字段值为空时不生成对应字段向量，但正式入库的合同必须具有视觉向量；视觉向量生成
失败时不得继续执行可能导致旧版本删除的替换操作。

> **向量职责不可互换：** `abstract_vector` 用于合同语义检索；`document_visual_vector` 用于近重复召回。二者使用不同输入与质量目标，不能相互替代。

同一个向量字段只能保存一个合同级向量。当前正式入库模块采用
`normalized_page_mean_v1`：PDF 全页逐页向量化，每个页向量先 L2 归一化，再等权平均并对
合同向量再次归一化。该策略不会静默截页，也不会用封面代替全文；正式采用前仍必须通过
压缩、删页、换页、重排和重新扫描样本评估召回率。若单页差异被平均明显稀释，再升级为
分块向量或独立页级索引，不在首个实验中提前引入多文档存储复杂度。

### 6.1 我方主体识别与对方公司元数据

入库模块通过环境变量 `CONTRACT_PROCESSOR_OWN_COMPANY_NAMES` 读取我方公司名称数组，值必须
是非空字符串组成的 JSON 数组。当前运行环境配置为：

```dotenv
CONTRACT_PROCESSOR_OWN_COMPANY_NAMES=["现象光伏","现象创新","phenosolar"]
```

数组元素既可以是完整公司名称，也可以是不会产生明显歧义的稳定简称。主体识别应先对候选
公司名称与配置名称执行 Unicode NFKC、大小写和首尾空白规范化，再判断候选名称是否包含任一
配置名称。中文名称允许简称包含匹配；纯英文名称必须按字母数字边界匹配，避免
`phenosolar` 误命中另一个更长且无关的英文单词。命中的主体视为我方并从对方公司名称集合
中排除，其余非空主体名称去重后形成 `counterparty_names` 元数据。该字段使用 SmartCN 支持
中文全文检索，并保留 keyword 子字段用于精确筛选；不再生成对方公司 dense vector。

未配置名称数组、数组格式非法或包含空元素属于入库模块启动配置错误。若一份终审合同没有
任何主体命中我方名称，系统不得依据买卖方角色猜测我方；应将该合同标记为主体识别未解决，
不生成错误的对方公司元数据，并在实验指标或正式接口响应中明确返回原因。多主体合同允许排除
多个我方主体，并将剩余多个外部主体共同视为对方集合。

> **主体识别失败必须显式暴露：** 未命中我方主体时，系统不得根据买卖方角色猜测；应保留失败原因，避免写入错误的对方公司元数据。

## 7. 安全替换

业务上采用“删除旧版本、录入新版本”，物理执行必须采用可补偿的安全顺序：

```text
写入并校验新 PDF
→ 写入新 ES 文档及向量
→ 将新版本设为当前版本
→ 删除旧 ES 文档和旧 PDF
→ 记录替换关系
```

不得先物理删除旧版本再尝试写入新版本，否则文件系统、Embedding 或 Elasticsearch 任一
步骤失败都会造成正式数据丢失。若新版本写入失败，旧版本必须继续保持可检索和可下载。

即使最终不保留旧 PDF 和旧元数据，也应保留最小替换记录：旧 `document_id`、新
`document_id`、操作人、时间和审核意见。

> **安全顺序：** 只有新 PDF 和新索引均成功且已激活后，才允许删除旧版本；任何前置步骤失败都必须保留旧版本。

## 8. 对外边界与依赖

当前已建立独立异步入库用例；未来接口输入为原始 PDF、完整终审对象及最小审核信息，输出
当前 `document_id` 和存储状态，判重与替换字段在对应能力实现后扩展。用例依赖以下端口：

- `SourceDocumentStore`：保存和读取 PDF；
- `ContractIndexRepository`：正式元数据、向量写入和回读；
- `ContractEmbeddingClient`：生成文本字段与合同视觉向量；
- `DuplicateContractJudge`：对新旧合同执行 VL 精判；
- 替换记录仓储：保存最小替换追溯信息。

这些端口均不得依赖 LangGraph。LangGraph 只在基础设施层表达入库节点拓扑；自动提取工作流
只负责产生待审核结果，不直接调用正式入库用例，前端终审完成后单独调用入库接口。

> **端口边界：** 端口定义不依赖 LangGraph；图只表达入库节点拓扑，不承担领域判重或替换决策。

## 9. 当前实现状态

当前已经具备待入库包络 DTO、正式 `IngestReviewedContract` 用例、独立四节点 LangGraph、
本地 PDF 存储和 ES9/LlamaIndex 正式适配器，已实现：

### 已完成

- 以终审 `value` 为准递归清理无效 Core、Attribute 与空子字段；
- 合同名称、产品名称和 Abstract 分字段向量化；排除我方后的对方名称只保存为文本元数据；
- PDF 所有页面分别视觉向量化并融合为单个 `document_visual_vector`；
- 自定义 LlamaIndex VectorStore 通过 ES9 官方异步客户端写入独立 strict mapping 索引；
- PDF 临时写入、哈希复核、原子激活和同 ID 幂等复用；
- 以 `ingestion_attempt_id` 按 `_id` 回读，以及不兼容 mapping/不可用主分片的快速失败。

`experiments/contract_ingestion_persistence/` 现在只调用正式用例并进行破坏范围受限的索引
重建和验收。现阶段仍不得据此宣称系统已经支持：

### 尚未实现

- VL 重复精判；
- `contract_id` 版本关联；
- 新旧合同的安全替换和补偿；
- 正式 FastAPI 路由和后台任务。

真实变体合同的视觉召回实验已验证当前小样本 Recall@5；后续仍需扩大合同集并确定 VL 判定
Schema。正式模块见[专家终审合同入库模块](../capabilities/contract-ingestion.md)，验收入口见
[终审合同入库实验模块](../experiments/contract-ingestion.md)。

> **实现状态边界：** 当前实验只验证已实现的正式入库链路；它不能证明业务判重、版本关联、安全替换或 HTTP 服务已经可用。

# 文档撰写风格手册

> **适用范围：** 本手册适用于 `description/` 下的架构、能力、参考契约、运行维护和实验说明文档。
>
> **目标：** 让重要信息易于扫描、易于追溯，并避免同一规则在多个文档中漂移。

---

## 1. 命名与位置

### 1.1 文件命名

| 位置 | 命名规则 | 示例 |
| --- | --- | --- |
| `description/` 顶层的全局入口或项目级规范 | 大写文件名；可使用下划线分隔词语 | `PROJECT.md`、`DOCUMENTATION_STYLE_GUIDE.md` |
| 任意子目录 | 小写 kebab-case；使用 `-`，不使用 `_` | `field-definition-contract.md`、`prompt-engineering.md` |

新文档应先按阅读目的归类，再选择目录；不要因为对应代码文件位于某处而机械放入同名目录。文档分层与阅读入口见[项目文档导航](README.md)。

### 1.2 单一权威来源

- 一项规则、契约或流程只能有一个完整的主文档。
- 其他文档只保留理解当前上下文所需的最小说明，并使用相对链接引用主文档。
- 修改主文档时，应检查引用它的文档是否仍然准确；不要复制粘贴后分别维护。

> **原则：** 项目总览负责回答“项目是什么”；专题文档负责回答“为什么、如何做”；机器可读定义与程序校验负责最终执行约束。

---

## 2. 页面结构与留白

### 2.1 标题层级

- 每个文件仅有一个一级标题（`#`），用于文档名称。
- 主主题使用二级标题（`##`）；只在该主题内部确有分支时使用三级标题（`###`）。
- 不为单一短段落增加标题；也不要跳过层级。
- 长文档应先提供“从哪里开始”或“与其他文档的关系”，帮助读者选择阅读路径。

### 2.2 分段与分割线

- 独立的大主题之间使用 `---` 分隔，尤其适用于项目级规范和长篇设计文档。
- 标题、正文、列表、表格、引用块和代码块之间均保留一个空行。
- 将连续的长段落拆为语义完整的短段落；不要为了凑行数机械换行。
- 一组平行规则优先使用列表；彼此独立且需要对比的信息优先使用表格。

---

## 3. Markdown 表达约定

### 3.1 引用块与强调

引用块用于读者需要立即注意的内容：强制要求、设计边界、优先级、风险提示或阅读提示。

```markdown
> **机器规范优先：** 缺少必要约束时必须失败，不能静默补默认值。
```

- 同一节最多突出一至两个关键结论；不要把普通正文全部放入引用块。
- 使用粗体突出短标签或关键术语，不用粗体包裹整段文字。
- 表示代码、字段名、状态值、路径和命令时使用反引号。

### 3.2 列表、表格与流程

| 场景 | 首选形式 |
| --- | --- |
| 有先后顺序、验收步骤或优先级 | 编号列表 |
| 平行规则、约束或阅读入口 | 无序列表 |
| 多项内容需要按相同维度比较 | 表格 |
| 多阶段工作流、数据流或状态流转 | `text` 代码块中的流程图 |
| 层级定义、字段说明或提示词输入 | YAML 代码块 |

表格中的单元格应保持简短；若需要说明复杂逻辑，使用表格后的段落或小节展开。流程图只表达关键分支和依赖，不在图中塞入实现细节。

### 3.3 代码与结构化示例

- 示例必须标明语言，例如 `yaml`、`json`、`text` 或 `python`。
- 用 YAML 或项目符号展示给模型阅读的字段定义、业务规则和判断要求；详细规则见[提示词工程规范](architecture/prompt-engineering.md)。
- JSON 用于机器接口、Schema、持久化契约或必须展示精确 JSON 语法的短示例；不要在提示词说明中粘贴大段 JSON。
- 示例只保留阐明当前规则所需的最小内容，避免与机器规范形成第二份完整定义。

## 4. 内容组织

### 4.1 项目总览

`PROJECT.md` 只保留项目定位、范围、术语、全局质量原则、总览流程和专题阅读入口。字段契约、算法细节、模块实现和运行操作应放入对应专题文档。

### 4.2 专题文档

一个功能或架构主题的文档通常应包含以下内容；可按实际复杂度裁剪，但不要省略必要边界：

1. 用途与适用范围。
2. 与其他模块或规范的关系。
3. 核心概念、流程或对外接口。
4. 关键实现与设计决策。
5. 依赖、配置、限制或验证方式。

### 4.3 参考契约

字段定义、状态机、DTO、索引 mapping 等精确规则应放在参考契约文档中。说明文字必须明确区分：

- 可由机器规范或运行产物直接观察的事实；
- 基于这些事实的设计判断或推断；
- 仍待确认、尚未实现或仅用于实验的内容。

---

## 5. 链接与维护

- 使用相对 Markdown 链接，并采用能说明目标内容的中文链接文本。
- 迁移或重命名文档时，必须同步更新所有入站链接、文档导航页和必要的锚点链接。
- 子目录中的文档改名为 kebab-case 时，同时检查代码、实验 README、配置注释和其他说明文档中的旧路径。
- 新建正式功能文档后，更新[项目文档导航](README.md)中的入口；不要在 `PROJECT.md` 重新维护长篇文档清单。

---

## 6. 写作与审查清单

提交文档前，确认：

- [ ] 文件位于正确的文档层级，命名符合本手册。
- [ ] 标题层级、空行、分割线和列表使页面易于扫描。
- [ ] 强制规则、边界和风险通过恰当的引用块突出。
- [ ] 规则没有在多个文档中重复；引用均指向唯一主文档。
- [ ] 表格、流程图、YAML 与 JSON 的使用符合各自适用场景。
- [ ] 相对链接、锚点和示例路径均有效。
- [ ] 文档中的实现状态、限制和实验结论与当前代码或原始产物一致。

> 文档的目标不是压缩信息量，而是让读者能快速找到正确层级，并在需要时追溯到完整依据。
